1 Pourquoi les branches ?

Sans branches, deux personnes qui modifient les mêmes fichiers en même temps créent immédiatement des conflits. C'est le chaos.

Sans branches — le chaos
# Alice pushes, Bob pushes...
! [rejected] main -> main
error: failed to push some refs
# → ils écrasent le travail l'un de l'autre
# → personne ne sait qui a fait quoi
# → le projet est cassé
Avec branches — chacun son espace
# Alice travaille sur feature/navbar
# Bob travaille sur feature/login
# → ils ne se bloquent jamais
# → chaque fonctionnalité est isolée
# → on fusionne quand c'est prêt
La règle d'or On ne travaille jamais directement sur main. main = la version stable. Chaque fonctionnalité = une branche. Toujours.

2 Vocabulaire à connaître

TermeC'est quoi ?Analogie
main La branche principale. C'est la version stable, celle qui tourne en production. Le tronc de l'arbre
branch Une copie parallèle du code pour travailler sur une fonctionnalité sans toucher main. Une branche de l'arbre
commit Une sauvegarde horodatée avec un message. Comme un checkpoint de jeu vidéo. Une photo de l'état du projet
push Envoyer ses commits vers GitHub (le serveur distant). Uploader son travail
pull Récupérer les derniers changements depuis GitHub. Télécharger le travail des autres
merge Fusionner une branche dans une autre. Coller deux morceaux ensemble
Pull Request Une demande de fusion sur GitHub. On demande à l'autre de relire avant de merger. Demander une validation avant de coller
conflit Deux personnes ont modifié les mêmes lignes. Git ne sait pas lequel garder. Deux personnes ont répondu sur la même ligne du cahier

3 Schéma visuel — ce qui se passe vraiment

Voici comment les branches d'Alice et Bob coexistent sur le même projet sans se perturber :

Ce que montre ce schéma Alice et Bob partent du même point (main). Ils travaillent en parallèle sur leurs branches sans se gêner. Quand chacun a terminé, on fusionne leurs branches dans main. Le résultat final contient le travail des deux.

4 Initialisation — Équipier 1 crée le projet

Une seule personne fait ça au début. L'autre rejoindra ensuite.

Équipier 1 — Alice (crée le repo)
1
Créer le repo sur GitHub

Aller sur github.com → New repository → Cocher "Add a README" → Create

2
Cloner en local et initialiser le projet

Sur son ordinateur, Alice clone le repo et pose la structure de base.

3
Inviter l'équipier sur GitHub

Settings → Collaborators → Add people → envoyer l'invitation à Bob

# Étape 1 — Alice clone le repo créé sur GitHub
git clone https://github.com/alice/mon-projet.git
cd mon-projet

# Étape 2 — Elle crée la structure de base
touch index.html style.css script.js

# Étape 3 — Premier commit sur main
git add .
git commit -m "init : structure de base du projet"
git push origin main
Important Alice envoie la structure de base sur main AVANT que Bob rejoigne. Comme ça, les deux partent du même point de départ.

5 Rejoindre le projet — Équipier 2

Équipier 2 — Bob (rejoint le repo)
# Bob accepte l'invitation GitHub (email ou notifications)
# Puis il clone le repo sur son ordinateur
git clone https://github.com/alice/mon-projet.git
cd mon-projet

# Vérifier qu'il voit bien le code d'Alice
ls
# → index.html  style.css  script.js  README.md

# Vérifier les branches disponibles
git branch -a
# → * main
#   remotes/origin/main
Bob est maintenant synchronisé avec Alice. Il a exactement le même code. Il peut maintenant créer sa propre branche pour travailler.

6 Le workflow quotidien — vue d'ensemble

Chaque matin, chaque jour de travail, le même rituel :

1
Se mettre à jour depuis main

git pull origin main — toujours commencer par récupérer le travail des autres

2
Créer ou se mettre sur sa branche

git checkout -b feature/ma-fonctionnalite — une branche = une fonctionnalité

3
Travailler, commiter régulièrement

git add . + git commit -m "message" — souvent, en petits morceaux

4
Pusher sa branche sur GitHub

git push origin feature/ma-fonctionnalite — sauvegarder sur le serveur

5
Ouvrir une Pull Request sur GitHub

Demander à l'équipier de relire le code avant de fusionner dans main

6
L'équipier relit et approuve

Il peut commenter, demander des modifications, puis valider

7
Merger dans main

Une fois validé, la branche fusionne dans main — le code est intégré

8
Supprimer la branche terminée

La branche a rempli son rôle. On la supprime pour garder le repo propre.

7 Équipier 1 — Alice travaille sur la navbar

Alice — feature/navbar

Début de journée — se mettre à jour

# Toujours commencer par ça !
git checkout main
git pull origin main
# → Alice récupère tout ce que Bob a pushé la veille

Créer sa branche de fonctionnalité

# Créer la branche ET basculer dessus en une seule commande
git checkout -b feature/navbar

# Vérifier sur quelle branche on est
git branch
# →   main
# → * feature/navbar   ← l'étoile = branche active

Travailler et commiter par petites étapes

# Alice modifie index.html, crée navbar.css...
# Après chaque petite étape logique → commit !

git add .
git commit -m "feat: ajout structure HTML navbar"

# Elle continue à coder...
git add .
git commit -m "style: mise en forme navbar responsive"

git add .
git commit -m "feat: ajout liens de navigation actifs"

Pusher sa branche sur GitHub

# Envoyer la branche sur GitHub
git push origin feature/navbar
# → La branche est maintenant visible sur GitHub
# → Bob peut la voir mais elle ne touche pas à main
Convention de nommage des branches feature/ pour une nouvelle fonctionnalité — fix/ pour corriger un bug — style/ pour du CSS — docs/ pour la documentation. Ça aide à comprendre l'intention au premier coup d'œil.

8 Équipier 2 — Bob travaille sur le formulaire

Bob — feature/login

Pendant qu'Alice fait la navbar, Bob fait le formulaire de login. En parallèle, sans attendre Alice.

# Bob se met à jour depuis main
git checkout main
git pull origin main

# Il crée SA branche
git checkout -b feature/login

# Il travaille et commite...
git add .
git commit -m "feat: structure HTML du formulaire login"

git add .
git commit -m "feat: validation JavaScript email + mot de passe"

git add .
git commit -m "style: design du formulaire responsive"

# Il push sa branche
git push origin feature/login
À ce stade Alice et Bob ont chacun leur branche sur GitHub. Ni l'une ni l'autre n'a touché à main. Le code principal est toujours propre et stable.

9 Fusionner — Pull Request sur GitHub

Quand une fonctionnalité est terminée et testée, on l'intègre dans main via une Pull Request (PR).

Étape 1 — Créer la Pull Request sur GitHub

1
Aller sur le repo GitHub

GitHub détecte automatiquement la nouvelle branche et propose un bouton "Compare & pull request". Cliquer dessus.

2
Remplir la PR

Titre clair + description de ce qui a été fait. Assigner l'équipier en reviewer.

3
L'équipier relit sur GitHub

Il voit les modifications fichier par fichier, peut commenter des lignes spécifiques, puis approuver.

4
Merger la PR

Cliquer sur "Merge pull request". La branche fusionne dans main.

5
Supprimer la branche

GitHub propose directement de supprimer la branche mergée. Cliquer sur "Delete branch".

Étape 2 — Se resynchroniser après le merge

# Les DEUX équipiers font ça après chaque merge dans main
git checkout main
git pull origin main
# → main est maintenant à jour avec le travail fusionné
# → Prêt à créer une nouvelle branche pour la prochaine fonctionnalité

Option — Merger en ligne de commande (sans PR)

# Si on veut merger directement depuis le terminal (pour les TP)
git checkout main
git pull origin main

# Merger la branche d'Alice dans main
git merge feature/navbar

# Pusher le merge sur GitHub
git push origin main

# Supprimer la branche localement
git branch -d feature/navbar

# Supprimer la branche sur GitHub aussi
git push origin --delete feature/navbar

10 Gérer les conflits

Un conflit arrive quand deux personnes modifient les mêmes lignes du même fichier. Git ne peut pas choisir automatiquement.

À quoi ressemble un conflit ?

# Git affiche ça dans le fichier en conflit :

<<<<<<< HEAD
<h1>Bienvenue sur MonApp</h1>

<h1>Mon Application Web</h1>
>>>>>>> feature/navbar

# ↑ Ce qui est entre <<<< et ==== = MA version (HEAD = branche actuelle)
# ↑ Ce qui est entre ==== et >>>> = la version de l'autre branche

Résoudre le conflit

1
Ouvrir le fichier en conflit dans VS Code

VS Code colore les conflits et propose des boutons : "Accept Current Change", "Accept Incoming Change", "Accept Both".

2
Choisir quelle version garder (ou combiner les deux)

Discuter avec l'équipier si besoin. Supprimer les marqueurs <<< === >>>.

3
Commiter la résolution

Une fois le conflit résolu, commiter pour valider la résolution.

# Après avoir résolu manuellement le conflit dans le fichier :
git add index.html
git commit -m "fix: résolution conflit sur le titre h1"
git push origin main
Éviter les conflits — la règle simple Si vous travaillez à deux, ne modifiez pas les mêmes fichiers en même temps. Alice prend les fichiers de layout, Bob prend les fichiers de fonctionnalité. La communication évite 90% des conflits.

11 Règles d'équipe à afficher dans votre repo

Alice
# Ce qu'Alice ne fait JAMAIS :
git push origin main
# → Pousser directement sur main
# → sans passer par une PR
git add .
git commit -m "fix"
# → Message de commit vide
# → ou sans description
# Ce qu'Alice DOIT faire :
git pull origin main
# → au début de chaque session
git checkout -b feature/xxx
# → toujours une branche dédiée
git commit -m "feat: description"
# → message clair et précis
Bob
# Ce que Bob ne fait JAMAIS :
git push --force
# → INTERDIT — écrase le travail de l'autre
git commit -m "wip"
git commit -m "test"
git commit -m "aaaaa"
# → Messages inutiles
# Ce que Bob DOIT faire :
git status
# → vérifier avant chaque commit
git log --oneline
# → voir l'historique propre
git branch
# → vérifier sa branche active
Commande interdite en duo git push --force ou git push -f est la commande la plus dangereuse qui existe en équipe. Elle écrase l'historique GitHub et détruit le travail de l'équipier. Ne jamais l'utiliser.

# Format recommandé : type: description courte

★ Scénario complet — une journée type en duo

Alice et Bob reprennent le travail le matin. Voici exactement ce que chacun tape :

Alice — matin
# 1. Se mettre à jour
git checkout main
git pull origin main

# 2. Nouvelle branche du jour
git checkout -b feature/footer

# 3. Elle code le footer...

# 4. Commits réguliers
git add .
git commit -m "feat: structure footer"
git add .
git commit -m "style: footer responsive"

# 5. Push
git push origin feature/footer
Bob — matin
# 1. Se mettre à jour
git checkout main
git pull origin main

# 2. Nouvelle branche du jour
git checkout -b feature/galerie

# 3. Il code la galerie d'images...

# 4. Commits réguliers
git add .
git commit -m "feat: grille galerie HTML"
git add .
git commit -m "style: galerie responsive"

# 5. Push
git push origin feature/galerie
Alice — après-midi (PR + merge)
# Alice ouvre une PR sur GitHub
# → feature/footer → main
# → Elle assigne Bob en reviewer

# Bob approuve → Alice merge sur GitHub

# Alice se resynchronise
git checkout main
git pull origin main
# ✓ main contient maintenant le footer
Bob — après-midi (PR + merge)
# Bob ouvre une PR sur GitHub
# → feature/galerie → main
# → Il assigne Alice en reviewer

# Alice approuve → Bob merge sur GitHub

# Bob se resynchronise
git checkout main
git pull origin main
# ✓ main contient footer + galerie
Résultat En une journée, Alice et Bob ont chacun développé une fonctionnalité complète, sans jamais se bloquer. main contient maintenant le footer ET la galerie. Propre, traçable, professionnel.
