Introduction

Architecture de sécurité MariaDB — le modèle utilisateurs

MariaDB utilise un système d'authentification à deux niveaux : qui peut se connecter (utilisateur + hôte) et ce qu'il peut faire (privilèges). Un utilisateur MariaDB n'est pas juste un nom — c'est une paire nom@hote.

MariaDB ├── Serveur port 3306, service mariadb │ ├── Utilisateurs stockés dans mysql.user │ ├── root@localhost super-admin, accès local uniquement │ ├── appuser@localhost accès local seulement │ ├── [email protected].% accès depuis un sous-réseau │ └── appuser@% accès depuis n'importe où (dangereux) │ ├── Bases de données │ ├── mysql système — droits, users (ne pas modifier) │ ├── information_schema métadonnées en lecture seule │ └── boutique votre base applicative │ └── Privilèges qui peut faire quoi sur quoi ├── Globaux *.* sur toutes les bases ├── Base boutique.* sur toute une base └── Table boutique.produits sur une table précise
!
root ne doit jamais être utilisé par une application. Le compte root a tous les droits sur tout le serveur. Une application web ne doit jamais se connecter avec root — créez toujours un utilisateur dédié avec uniquement les droits nécessaires.

Se connecter au serveur MariaDB en ligne de commande :

Terminal — connexion au serveurShell
# Connexion en tant que root (local)
$ mariadb -u root -p
#         -u root  = utilisateur root
#         -p       = demander le mot de passe

# Connexion avec un utilisateur spécifique sur une base précise
$ mariadb -u appuser -p boutique
#                       ^ base de données cible

# Connexion sur un hôte distant
$ mariadb -h 192.168.1.10 -u appuser -p boutique

# Vérifier la version
$ mariadb --version
Premières commandes dans le shell MariaDBSQL
-- Lister toutes les bases de données
SHOW DATABASES;

-- Sélectionner une base
USE boutique;

-- Lister les tables de la base courante
SHOW TABLES;

-- Voir tous les utilisateurs du serveur
SELECT User, Host FROM mysql.user;

-- Quitter
EXIT;
i
MariaDB vs MySQL. MariaDB est un fork de MySQL créé en 2009. Les commandes d'administration sont quasi identiques. Sur Debian/Ubuntu, le service s'appelle mariadb (pas mysql). Le client en ligne de commande est mariadb (ou mysql selon les versions).
01
Gestion des utilisateurs

Créer un utilisateur — CREATE USER

La commande CREATE USER crée un compte sans aucun privilège. L'utilisateur peut se connecter mais ne voit rien. Les droits sont attribués séparément avec GRANT. Cette séparation est intentionnelle : elle force à réfléchir à ce qu'on accorde.

Syntaxe CREATE USER — exemples progressifsSQL
-- Syntaxe de base
CREATE USER 'nom_utilisateur'@'hote' IDENTIFIED BY 'mot_de_passe';

-- Exemple 1 : accès local uniquement (recommandé pour les apps web)
CREATE USER 'appuser'@'localhost' IDENTIFIED BY 'MotDePasse_S3cur!';

-- Exemple 2 : accès depuis une IP précise
CREATE USER 'reporter'@'192.168.1.42' IDENTIFIED BY 'ReportPass2024!';

-- Exemple 3 : accès depuis un sous-réseau (wildcard %)
CREATE USER 'devteam'@'192.168.1.%' IDENTIFIED BY 'DevPass_99!';
--                              % = n'importe quelle valeur dans ce segment

-- Exemple 4 : depuis n'importe où (DÉCONSEILLÉ en production)
CREATE USER 'testuser'@'%' IDENTIFIED BY 'TestPass!';

-- Vérifier que l'utilisateur a bien été créé
SELECT User, Host, authentication_string FROM mysql.user
WHERE User = 'appuser';
La paire utilisateur@hote — pourquoi c'est important
appuser@localhost et appuser@% sont deux comptes distincts pour MariaDB, même s'ils ont le même nom. Ils peuvent avoir des mots de passe et des droits différents. Quand un utilisateur se connecte, MariaDB cherche l'entrée la plus précise qui correspond à son IP.

Ordre de priorité : IP exacte > sous-réseau > hostname > %
!
Mots de passe forts obligatoires. MariaDB peut avoir une politique de validation des mots de passe (plugin validate_password). En production, utilisez au minimum 12 caractères avec majuscules, minuscules, chiffres et caractères spéciaux. Ne jamais utiliser le mot de passe dans un script versionné — utilisez des variables d'environnement ou un fichier .my.cnf hors dépôt.
Fichier .my.cnf — eviter de taper le mot de passeConfig
# ~/.my.cnf — fichier de configuration personnel (chmod 600)
[client]
user     = appuser
password = MotDePasse_S3cur!
host     = localhost

# Avec ce fichier, on peut se connecter sans saisir les identifiants :
$ mariadb boutique
# Au lieu de : mariadb -u appuser -p boutique

# Sécuriser le fichier
$ chmod 600 ~/.my.cnf
OK
A retenir : un utilisateur est toujours une paire nom@hote. Après CREATE USER, l'utilisateur n'a aucun droit. Les droits s'attribuent avec GRANT. Toujours préférer localhost à %.
02
Gestion des droits

GRANT — attribuer des privilèges

GRANT est la commande centrale de la gestion des droits. Elle suit toujours la même structure : quels privilèges, sur quoi, pour qui. Le principe de moindre privilège est la règle d'or : n'accorder que ce qui est strictement nécessaire.

Syntaxe GRANT — structureSQL
GRANT privilege1, privilege2, ...
ON base_de_donnees.table
TO 'utilisateur'@'hote';

--  ON base.*    → toutes les tables de la base
--  ON *.*       → toutes les bases, toutes les tables (global)
--  ON base.tab  → une table précise
Exemples GRANT selon les profilsSQL
-- Profil 1 : application web (lecture + écriture, pas de structure)
GRANT SELECT, INSERT, UPDATE, DELETE
ON boutique.*
TO 'appuser'@'localhost';

-- Profil 2 : lecture seule (rapports, BI, monitoring)
GRANT SELECT
ON boutique.*
TO 'reporter'@'192.168.1.42';

-- Profil 3 : développeur (tout sur une base, pas d'admin)
GRANT SELECT, INSERT, UPDATE, DELETE,
      CREATE, DROP, ALTER, INDEX
ON dev_boutique.*
TO 'devteam'@'192.168.1.%';

-- Profil 4 : administrateur de base (tous droits sur une base)
GRANT ALL PRIVILEGES
ON boutique.*
TO 'dbadmin'@'localhost';

-- INDISPENSABLE après tout GRANT : appliquer les changements
FLUSH PRIVILEGES;
-- Dans les versions récentes, automatique après GRANT/REVOKE
-- Mais bonne pratique de toujours le faire

Les privilèges disponibles — classés du moins au plus dangereux :

PrivilègeLectureDonnéesStructureAdminUsage courant
SELECTOui———Lire des données. Base de tout accès.
INSERT—Oui——Insérer des lignes.
UPDATE—Oui——Modifier des lignes existantes.
DELETE—Oui——Supprimer des lignes.
CREATE——Oui—Créer des tables et bases.
DROP——Oui—Supprimer tables et bases. Dangereux.
ALTER——Oui—Modifier la structure des tables.
INDEX——Oui—Créer et supprimer des index.
EXECUTE——Proc—Exécuter procédures stockées.
GRANT OPTION———OuiDonner ses propres droits à d'autres. Très dangereux.
ALL PRIVILEGESOuiOuiOuiOuiTout. Réserver aux admins de base.
i
Principe de moindre privilège. Une application de boutique en ligne n'a besoin que de SELECT, INSERT, UPDATE, DELETE. Jamais de CREATE, DROP ou ALTER en production — ces opérations se font par des migrations dédiées exécutées par un utilisateur de déploiement séparé, pas par l'utilisateur applicatif.

04
Gestion des utilisateurs

Modifier, révoquer, supprimer

Trois opérations courantes sur les utilisateurs : changer le mot de passe, révoquer des privilèges avec REVOKE, et supprimer définitivement un compte avec DROP USER.

Modifier un mot de passeSQL
-- Méthode recommandée (MariaDB 10.4+)
ALTER USER 'appuser'@'localhost'
IDENTIFIED BY 'NouveauMotDePasse_2024!';

-- Ancienne syntaxe (encore valide)
SET PASSWORD FOR 'appuser'@'localhost'
    = PASSWORD('NouveauMotDePasse_2024!');

-- Changer son propre mot de passe (utilisateur connecté)
SET PASSWORD = PASSWORD('MonNouveauMdp!');

FLUSH PRIVILEGES;
REVOKE — retirer des privilègesSQL
-- Retirer un privilège précis
REVOKE DELETE
ON boutique.*
FROM 'appuser'@'localhost';

-- Retirer plusieurs privilèges
REVOKE INSERT, UPDATE, DELETE
ON boutique.*
FROM 'reporter'@'192.168.1.42';

-- Retirer tous les privilèges d'une base
REVOKE ALL PRIVILEGES
ON boutique.*
FROM 'appuser'@'localhost';
-- Note : l'utilisateur existe toujours, il n'a plus de droits

FLUSH PRIVILEGES;
DROP USER — supprimer un compteIrréversible
-- Supprimer un utilisateur (ses droits sont aussi supprimés)
DROP USER 'appuser'@'localhost';

-- Supprimer plusieurs utilisateurs
DROP USER
    'appuser'@'localhost',
    'reporter'@'192.168.1.42';

-- Supprimer si existe (évite une erreur si absent)
DROP USER IF EXISTS 'ancienuser'@'localhost';

FLUSH PRIVILEGES;
!
DROP USER supprime aussi les droits associés dans mysql.user et mysql.db. C'est différent de REVOKE ALL qui laisse le compte exister sans droits. Si l'utilisateur est connecté au moment du DROP, sa session reste active jusqu'à déconnexion — il ne peut plus se reconnecter ensuite.
!
Bloquer temporairement un compte sans le supprimer. Depuis MariaDB 10.4, on peut verrouiller un compte sans le supprimer : ALTER USER 'appuser'@'localhost' ACCOUNT LOCK;. Pour déverrouiller : ACCOUNT UNLOCK;. Utile pour désactiver temporairement un accès sans perdre les droits configurés.
05
Audit et vérification

Consulter les droits — SHOW GRANTS

Avant de modifier des droits, il faut savoir ce qui existe. SHOW GRANTS affiche exactement les commandes GRANT qui recréeraient la configuration actuelle d'un utilisateur. C'est aussi la commande d'audit fondamentale.

SHOW GRANTS — lire les droitsSQL
-- Droits de l'utilisateur courant (vous-même)
SHOW GRANTS;

-- Droits d'un utilisateur spécifique
SHOW GRANTS FOR 'appuser'@'localhost';

-- Résultat typique :
-- +------------------------------------------------------------+
-- | Grants for appuser@localhost                               |
-- +------------------------------------------------------------+
-- | GRANT USAGE ON *.* TO 'appuser'@'localhost'                |
-- | GRANT SELECT, INSERT, UPDATE, DELETE ON `boutique`.* TO   |
-- |   'appuser'@'localhost'                                    |
-- +------------------------------------------------------------+

-- Note : GRANT USAGE signifie "peut se connecter mais rien d'autre"
-- C'est le droit de base présent même avec un compte vide
Audit complet — vue d'ensemble de tous les droitsSQL
-- Tous les utilisateurs et leurs hôtes
SELECT User, Host, account_locked
FROM mysql.user
ORDER BY User;

-- Droits par base de données
SELECT User, Host, Db,
       Select_priv, Insert_priv, Update_priv,
       Delete_priv, Create_priv, Drop_priv
FROM mysql.db
ORDER BY User, Db;

-- Vérifier si un utilisateur peut accéder à une base précise
SELECT User, Host, Db,
       Select_priv, Insert_priv
FROM mysql.db
WHERE Db = 'boutique';
OK
Workflow de gestion des droits : SHOW GRANTS → identifier ce qui existe → REVOKE ce qui est en trop → GRANT ce qui manque → FLUSH PRIVILEGES → SHOW GRANTS pour vérifier.
06
Sauvegarde

mysqldump — sauvegarder une base

mysqldump est l'outil standard de sauvegarde logique de MariaDB. Il génère un fichier SQL contenant toutes les instructions nécessaires pour recréer la base : structure des tables, données, vues, procédures. C'est une sauvegarde lisible et portable.

i
Sauvegarde logique vs physique. mysqldump produit une sauvegarde logique : un fichier texte SQL. C'est portable, facile à inspecter, mais lent sur de très grandes bases. Pour les bases volumineuses (> 50 Go), mariabackup (sauvegarde physique) est plus adapté.
mysqldump — exemples essentielsShell
# Sauvegarder une base complète (structure + données)
$ mysqldump -u root -p boutique > boutique_backup.sql

# Sauvegarder avec compression (recommandé)
$ mysqldump -u root -p boutique | gzip > boutique_$(date +%Y%m%d).sql.gz

# Sauvegarder plusieurs bases
$ mysqldump -u root -p --databases boutique catalogue > multi_backup.sql

# Sauvegarder TOUTES les bases (y compris mysql, users, droits)
$ mysqldump -u root -p --all-databases > full_backup.sql

# Sauvegarder uniquement la structure (sans les données)
$ mysqldump -u root -p --no-data boutique > boutique_structure.sql

# Sauvegarder uniquement les données (sans la structure)
$ mysqldump -u root -p --no-create-info boutique > boutique_data.sql

# Sauvegarder une seule table
$ mysqldump -u root -p boutique produits > produits_backup.sql

# Sauvegarde complète avec options de fiabilité (production)
$ mysqldump -u root -p \
    --single-transaction \
    --routines \
    --triggers \
    --events \
    boutique | gzip > boutique_$(date +%Y%m%d_%H%M).sql.gz
OptionRôleUsage
--single-transactionSauvegarde cohérente sans verrouiller les tables (InnoDB)Production obligatoire
--routines (-R)Inclure les procédures et fonctions stockéesSi vous utilisez des stored procedures
--triggersInclure les triggers (déclencheurs)Inclus par défaut, option pour l'exclure
--events (-E)Inclure les évènements planifiés (cron SQL)Si vous utilisez EVENT SCHEDULER
--no-data (-d)Structure seulement, pas de donnéesPartager le schéma sans les données
--all-databases (-A)Toutes les bases + mysql.user (droits)Migration serveur complète
--compress (-C)Compression du flux client-serveurSauvegarde depuis un serveur distant
!
--single-transaction est indispensable sur InnoDB. Sans cette option, mysqldump pose des verrous sur toutes les tables pendant la sauvegarde — votre application est bloquée en écriture. Avec --single-transaction, la sauvegarde se fait dans une transaction isolée : cohérente et sans blocage. Cela ne fonctionne qu'avec InnoDB (pas MyISAM).
Cron job — automatiser la sauvegarde quotidienneShell
# Éditer la crontab : crontab -e
# Sauvegarde tous les jours à 3h00
0 3 * * * mysqldump -u backupuser -pMotDePasse \
    --single-transaction --routines boutique \
    | gzip > /var/backups/mariadb/boutique_$(date +\%Y\%m\%d).sql.gz

# Purger les sauvegardes de plus de 30 jours
0 4 * * * find /var/backups/mariadb/ -name "*.sql.gz" -mtime +30 -delete

# Créer un utilisateur dédié aux sauvegardes (lecture seule)
-- Dans MariaDB :
CREATE USER 'backupuser'@'localhost' IDENTIFIED BY 'BackupPass!';
GRANT SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER
ON boutique.*
TO 'backupuser'@'localhost';
FLUSH PRIVILEGES;
07
Restauration

Restaurer une sauvegarde

La restauration consiste à rejouer le fichier SQL sur le serveur. MariaDB exécute les instructions dans l'ordre : DROP TABLE, CREATE TABLE, INSERT. La base est recréée à l'état exact de la sauvegarde.

!
Une restauration écrase les données existantes. Si la base cible existe et contient des données, les INSERT du fichier SQL les remplaceront (ou généreront des erreurs de doublon). Toujours restaurer sur une base vide ou avec --add-drop-database dans la sauvegarde.
Étape 1 — Préparer la base cible
Créer une base vide si elle n'existe pas, ou vider l'existante avant de restaurer.
CREATE DATABASE IF NOT EXISTS boutique;
Étape 2 — Décompresser si nécessaire
Si la sauvegarde est compressée (.sql.gz), décompresser avant ou utiliser zcat en pipe.
gunzip boutique_20241215.sql.gz
Étape 3 — Importer le fichier SQL
Rejouer le fichier SQL sur la base cible.
mariadb -u root -p boutique < boutique_backup.sql
Étape 4 — Vérifier la restauration
Contrôler que les tables existent et contiennent le bon nombre de lignes.
SHOW TABLES; SELECT COUNT(*) FROM produits;
Commandes de restauration — tous les casShell
# Restauration basique (fichier .sql non compressé)
$ mariadb -u root -p boutique < boutique_backup.sql

# Restauration depuis un fichier compressé (sans décompresser)
$ zcat boutique_20241215.sql.gz | mariadb -u root -p boutique

# Restauration avec création automatique de la base
# (nécessite que le dump ait été fait avec --databases ou --all-databases)
$ mariadb -u root -p < boutique_backup.sql

# Restauration vers une base différente (renommer à la volée)
# Étape 1 : créer la nouvelle base
$ mariadb -u root -p -e "CREATE DATABASE boutique_restore;"
# Étape 2 : importer
$ mariadb -u root -p boutique_restore < boutique_backup.sql

# Restauration d'une seule table depuis un dump complet
# Extraire la table 'produits' du dump avec grep
$ grep -n "Table structure for table \`produits\`" boutique_backup.sql
# Puis extraire les lignes correspondantes manuellement ou :
$ mariadb -u root -p boutique \
    -e "SET FOREIGN_KEY_CHECKS=0; DROP TABLE IF EXISTS produits;"
$ mariadb -u root -p boutique < produits_backup.sql

# Vérifier après restauration
$ mariadb -u root -p boutique \
    -e "SHOW TABLES; SELECT COUNT(*) FROM produits;"
Script de restauration sécuriséScript bash
#!/bin/bash
# restore.sh — restauration avec vérifications

DB_NAME="boutique"
BACKUP_FILE="$1"
DB_USER="root"

if [ -z "$BACKUP_FILE" ]; then
    echo "Usage: ./restore.sh fichier_backup.sql[.gz]"
    exit 1
fi

if [ ! -f "$BACKUP_FILE" ]; then
    echo "ERREUR : fichier introuvable : $BACKUP_FILE"
    exit 1
fi

echo "Restauration de $BACKUP_FILE vers $DB_NAME..."
echo "ATTENTION : cela va ecraser les données existantes."
read -p "Confirmer ? (oui/non) : " CONFIRM

if [ "$CONFIRM" != "oui" ]; then
    echo "Annulé."; exit 0
fi

# Décompresser ou restaurer directement
if [[ "$BACKUP_FILE" == *.gz ]]; then
    zcat "$BACKUP_FILE" | mariadb -u $DB_USER -p $DB_NAME
else
    mariadb -u $DB_USER -p $DB_NAME < "$BACKUP_FILE"
fi

echo "Restauration terminée."

Bonnes pratiques

Stratégies de sauvegarde — la règle 3-2-1

Une sauvegarde qui n'a jamais été testée n'est pas une sauvegarde — c'est une espérance. La stratégie de sauvegarde doit répondre à deux questions : quelle est la perte de données maximale acceptable (RPO) et en combien de temps doit-on être de nouveau opérationnel (RTO) ?

Règle 3-2-1 ├── 3 copies des données │ l'originale + 2 sauvegardes ├── 2 supports différents │ disque local + NAS, ou disque + cloud └── 1 copie hors site cloud, autre datacenter, autre bâtiment physique RPO / RTO ├── RPO (Recovery Point Objective) │ perte de données max acceptable │ Ex : RPO = 1h → sauvegarde toutes les heures └── RTO (Recovery Time Objective) temps max pour être de nouveau opérationnel Ex : RTO = 4h → procédure de restauration testée et < 4h
Type de sauvegardeFréquenceRétentionAvantagesInconvénients
Complète quotidienne 1x/jour (nuit) 7 à 30 jours Simple, restauration directe Volumineux, prend du temps
Incrémentale horaire 1x/heure 24-48 heures RPO court, petit volume Restauration plus complexe
Binary logs (PITR) En continu 3-7 jours Restauration à la minute près Configuration complexe
Snapshot Cloud 1x/jour ou + Paramétrable Hors site automatique Coût selon volume
+
Tester la restauration régulièrement. Planifiez un test de restauration mensuel sur un environnement de staging. Un fichier .sql.gz corrompu ou une restauration qui échoue après un incident n'est découvert qu'au moment où on en a le plus besoin. La procédure de restauration doit être documentée et connue de toute l'équipe.
!
Surveiller la taille et la durée des sauvegardes. Si votre dump passe soudainement de 200 Mo à 20 Mo ou si son temps d'exécution change brutalement, c'est un signal d'alerte. Ajoutez une vérification de taille minimale dans vos scripts de sauvegarde et envoyez une alerte si le fichier est anormalement petit.
