1 L'arborescence — comment ranger ses fichiers PHP
Pourquoi ranger ses fichiers ? Un projet PHP mal rangé devient vite ingérable. L'objectif est de séparer ce qui appartient au serveur (PHP, config, BDD) de ce qui appartient au navigateur (CSS, JS, images) et d'éviter que des fichiers sensibles soient accessibles depuis le web.

  index.php ← point d'entrée, inclut tout

    footer.php ← </body></html>

  📁 pages/ ← pages du site

  📁 assets/ ← CSS, images, JS (accessible depuis le navigateur)

⚠️
Le dossier includes/ ne doit jamais contenir de fichiers visitables directement par l'URL. Il ne contient que des fragments PHP inclus par d'autres pages. connexion.php ne doit surtout pas être accessible depuis le navigateur !
2 include vs require — quelle différence ?
La question clé : Si le fichier inclus est introuvable, que se passe-t-il ? C'est là que include et require se comportent différemment.
Fonction Si le fichier est introuvable... L'exécution continue ? Quand l'utiliser
include ⚠️ Warning (avertissement), mais continue OUI Fichiers optionnels (widget, bannière...)
require 💥 Fatal Error — stoppe tout NON Fichiers indispensables (connexion BDD, config...)
include_once ⚠️ Warning, mais continue OUI Fichiers optionnels, jamais deux fois
require_once 💥 Fatal Error NON Fichiers critiques, jamais deux fois ✅ le plus utilisé
❌ include — fichier manquant → continue quand même
<?php
// widgets/pub.php n'existe pas
include 'widgets/pub.php';

// Warning dans les logs, mais ça continue
echo "La page s'affiche quand même !";
// → Utile si c'est un widget optionnel
💥 require — fichier manquant → TOUT s'arrête
<?php
// connexion.php est introuvable
require 'includes/connexion.php';

// Fatal Error : la page est blanche
// Rien en dessous ne s'exécute
echo "Ce code ne s'exécute jamais";
✅
Règle simple à retenir : utilise toujours require_once dans 99% des cas. Si le fichier est indispensable (connexion BDD, config, header), il vaut mieux que tout s'arrête plutôt qu'afficher une page cassée ou pleine d'erreurs SQL.
💡
Quand utiliser include ? Uniquement quand le fichier est vraiment optionnel : une bannière promo, un widget de météo, une sidebar... Sa disparition ne casse pas le site.
Ce qui se passe quand PHP lit un require_once :
Fichier appelant

require_once
connexion.php
require_once
header.php
Résultat final

🧩
PHP lit le fichier appelant de haut en bas. Chaque fois qu'il rencontre un require_once, il copie-colle le contenu du fichier inclus à cet endroit, comme si tu avais tout écrit dans un seul fichier. Le résultat final est une seule page HTML complète.
3 Pourquoi _once ? Le danger des inclusions multiples
Le problème : Imagine que tu inclus connexion.php dans deux fichiers différents, et que ces deux fichiers sont eux-mêmes inclus dans index.php. Sans _once, la connexion PDO sera créée deux fois → erreur !
❌ Sans _once — double inclusion
<?php
// index.php
require 'includes/connexion.php';
// ↑ $pdo est créé une 1ère fois

require 'includes/header.php';
// header.php fait aussi :
// require 'connexion.php'
// ↑ $pdo est créé une 2ème fois !
// → Variable redéfinie, erreur possible
✅ Avec _once — inclus une seule fois
<?php
// index.php
require_once 'includes/connexion.php';
// ↑ $pdo créé, PHP mémorise

require_once 'includes/header.php';
// header.php fait aussi :
// require_once 'connexion.php'
// ↑ PHP dit "déjà inclus, j'ignore"
// → Aucune erreur ✅
⚠️
Règle d'or : Utilise toujours require_once et jamais require seul (sauf cas très particuliers). Le _once ne coûte rien et évite des bugs difficiles à trouver.

4 Les chemins — comment écrire le bon chemin ?
C'est souvent là que les apprenants bloquent ! Le chemin dans le require_once est toujours relatif à l'emplacement du fichier qui fait l'appel, pas à la racine du projet.
📁 mon-projet/
  index.php ← je suis ICI
  📁 includes/
    connexion.php
  📁 pages/
    produits.php ← ou je suis ICI
📄 Depuis index.php (à la racine)
<?php
// index.php est à la racine
// includes/ est juste à côté

require_once 'includes/connexion.php';
//            ↑ chemin direct
//            on descend dans includes/
📄 Depuis pages/produits.php (sous-dossier)
<?php
// produits.php est dans pages/
// Il faut d'abord remonter d'un niveau

require_once '../includes/connexion.php';
//            ↑ ../ = remonter d'un niveau
//            puis descendre dans includes/
🗺️
La règle des chemins relatifs :
  includes/fichier.php → descend dans le dossier includes
  ../includes/fichier.php → remonte d'un niveau (../), puis descend dans includes
  ../../includes/fichier.php → remonte de deux niveaux, etc.
✅ Solution propre : utiliser __DIR__
<?php
// __DIR__ = chemin absolu du dossier du fichier courant
// Fonctionne peu importe d'où on l'appelle !

// Dans pages/produits.php :
require_once __DIR__ . '/../includes/connexion.php';

// Dans index.php :
require_once __DIR__ . '/includes/connexion.php';

// __DIR__ vaut par exemple : /Applications/MAMP/htdocs/mon-projet/pages
// Le chemin final sera toujours exact, même si tu déplaces le projet
⭐
Bonne pratique : utilise __DIR__ + concaténation . pour construire tes chemins. C'est plus robuste que les chemins relatifs simples, surtout quand le projet grossit.
5 header() — la redirection PHP
Ne pas confondre ! Il y a deux "header" en PHP : includes/header.php (ton fichier HTML) et la fonction PHP header() qui envoie des en-têtes HTTP, notamment pour rediriger l'utilisateur vers une autre page.
🔀 header() — redirection
<?php
// Redirige vers une autre page
header('Location: index.php');
exit(); // TOUJOURS après header() !

// Redirection vers une URL absolue
header('Location: https://monsite.fr/accueil.php');
exit();

// Redirection avec paramètre GET
header('Location: produits.php?message=ajoute');
exit();
❌ L'erreur la plus fréquente
<?php
// ERREUR : du HTML ou echo AVANT header()
echo "Bonjour !"; // ← envoie déjà du contenu

header('Location: index.php');
// ↑ Warning : "Cannot modify header information
//   - headers already sent"
// La redirection ne fonctionne pas !
🚨
Règle absolue : header() doit être appelé avant tout affichage. Pas de echo, pas de HTML, pas même une ligne vide ou un espace avant <?php ! Sinon PHP a déjà commencé à envoyer la réponse et ne peut plus changer les en-têtes.
Cas d'utilisation typiques de header()
📋 Scénarios réels
✅ Redirection après une connexion réussie
<?php
session_start(); // Toujours en tout premier !

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $email = $_POST['email']   ?? '';
    $mdp   = $_POST['password'] ?? '';

    // On vérifie en base de données...
    $user = verifierUtilisateur($email, $mdp);

    if ($user) {
        $_SESSION['user_id'] = $user['id'];
        header('Location: index.php'); // ← Redirection !
        exit();
    } else {
        $erreur = "Email ou mot de passe incorrect";
        // Pas de redirection → on reste sur la page de login
    }
}
📝 Après soumission d'un formulaire (pattern PRG)
<?php
// ajouter-produit.php
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    // Traitement du formulaire...
    $stmt = $pdo->prepare('INSERT INTO produits ...');
    $stmt->execute([...]);

    // Pattern PRG : Post → Redirect → Get
    // Évite la double soumission si l'utilisateur recharge la page
    header('Location: produits.php?message=ajoute');
    exit();
}

// Dans produits.php, on lit le message :
if (isset($_GET['message']) && $_GET['message'] === 'ajoute') {
    echo "<p class='success'>Produit ajouté !</p>";
}
🔒 Protéger une page (vérifier si connecté)
<?php
// En haut de chaque page protégée
session_start();

if (!isset($_SESSION['user_id'])) {
    // Pas connecté → on redirige vers la page de login
    header('Location: login.php');
    exit(); // ← INDISPENSABLE !
}

// Si on arrive ici, l'utilisateur EST connecté
// On peut afficher le contenu protégé

// Astuce : mettre ce bloc dans un fichier
// includes/auth.php et faire require_once dessus
🚪 Déconnexion
<?php
// logout.php — page de déconnexion
session_start();

// Détruire toutes les données de session
session_unset();
session_destroy();

// Rediriger vers l'accueil ou le login
header('Location: login.php');
exit();
// Ne jamais oublier exit() après header() !
💡
Toujours mettre exit() après header('Location: ...') ! Sans exit(), PHP continue d'exécuter le code qui suit la redirection. L'utilisateur est redirigé dans le navigateur mais le serveur a quand même exécuté tout le reste du script — ce qui peut causer des effets de bord indésirables.
