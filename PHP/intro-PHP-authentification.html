!
Ne jamais stocker un mot de passe en clair ou en MD5/SHA1. Ces fonctions sont reversibles ou craqueables par brute-force. password_hash() avec PASSWORD_BCRYPT genere un hash salte et couteux a calculer. C'est la seule methode acceptable.
01
Etape 1

Table utilisateurs

La table utilisateurs stocke l'email (unique), le hash bcrypt du mot de passe (jamais le mot de passe lui-meme), le role et les champs pour le "Se souvenir de moi".

SQL — table utilisateursSQL
CREATE TABLE IF NOT EXISTS utilisateurs (
    id           INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    nom          VARCHAR(100)  NOT NULL,
    email        VARCHAR(180)  NOT NULL UNIQUE,
    mot_de_passe VARCHAR(255)  NOT NULL,
    -- VARCHAR(255) obligatoire : bcrypt genere 60 chars
    -- mais la longueur peut changer avec futurs algos
    role         ENUM('user', 'admin') NOT NULL DEFAULT 'user',
    remember_token  VARCHAR(100) NULL DEFAULT NULL,
    token_expire_le DATETIME       NULL DEFAULT NULL,
    cree_le      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
!
VARCHAR(255) pour le hash. password_hash() avec bcrypt genere actuellement un hash de 60 caracteres. On reserve 255 pour etre compatible avec les futurs algorithmes (Argon2, etc.) qui peuvent etre plus longs. Ne jamais mettre VARCHAR(60).
02
Etape 2

Inscription

L'inscription valide les donnees, hache le mot de passe avec PASSWORD_BCRYPT, insere en BDD et gere le cas d'un email deja utilise via le code SQLSTATE 23000.

AuthController.php — methode register()PHP
<?php
// AuthController.php — methode register()

public function register(): void {

    if ($_SERVER['REQUEST_METHOD'] === 'POST') {

        // 1. Valider le token CSRF
        $this->verifyCsrf($_POST['csrf_token'] ?? '');

        // 2. Valider les donnees
        $nom   = trim($_POST['nom'] ?? '');
        $email = trim(strtolower($_POST['email'] ?? ''));
        $pass  = $_POST['mot_de_passe'] ?? '';
        $pass2 = $_POST['confirmation'] ?? '';

        $errors = [];
        if (strlen($nom) < 2)                          $errors[] = 'Nom trop court';
        if (!filter_var($email, FILTER_VALIDATE_EMAIL))   $errors[] = 'Email invalide';
        if (strlen($pass) < 8)                           $errors[] = '8 caracteres minimum';
        if ($pass !== $pass2)                            $errors[] = 'Mots de passe differents';

        if (empty($errors)) {
            try {
                // 3. Hasher le mot de passe avec bcrypt
                $hash = password_hash($pass, PASSWORD_BCRYPT);

                // 4. Inserer en BDD
                $stmt = $this->pdo->prepare(
                    'INSERT INTO utilisateurs (nom, email, mot_de_passe) VALUES (?, ?, ?)'
                );
                $stmt->execute([$nom, $email, $hash]);

                // 5. Rediriger vers la connexion
                header('Location: /login?registered=1');
                exit;

            } catch (PDOException $e) {
                // Email deja utilise (contrainte UNIQUE)
                if ($e->getCode() === '23000') {
                    $errors[] = 'Cet email est deja utilise';
                } else {
                    throw $e;
                }
            }
        }
    }

    $this->render('auth/register', ['errors' => $errors ?? [], 'old' => $_POST]);
}

i
password_hash() avec PASSWORD_BCRYPT. Bcrypt est lent intentionnellement (facteur de cout par defaut = 10, soit ~100ms). Cela rend les attaques par brute-force extremement couteuses. Le hash genere contient le sel et le facteur de cout : $2y$10$.... On n'a pas besoin de stocker le sel separement.
03
Etape 3

Connexion

La connexion recupere l'utilisateur par email, compare le mot de passe avec password_verify(), regenere l'ID de session pour se proteger contre la fixation de session, puis remplit $_SESSION.

AuthController.php — methode login()PHP
<?php
public function login(): void {

    if ($_SERVER['REQUEST_METHOD'] === 'POST') {

        $this->verifyCsrf($_POST['csrf_token'] ?? '');

        $email = trim(strtolower($_POST['email'] ?? ''));
        $pass  = $_POST['mot_de_passe'] ?? '';

        // 1. Chercher l'utilisateur par email
        $stmt = $this->pdo->prepare('SELECT * FROM utilisateurs WHERE email = ?');
        $stmt->execute([$email]);
        $user = $stmt->fetch();

        // 2. Verifier le mot de passe
        // password_verify() est lent expres → protection timing attack
        if ($user && password_verify($pass, $user['mot_de_passe'])) {

            // 3. Regenerer l'ID de session (protection session fixation)
            session_regenerate_id(true);

            // 4. Stocker les infos de l'utilisateur en session
            $_SESSION['user_id']    = $user['id'];
            $_SESSION['user_nom']   = $user['nom'];
            $_SESSION['user_role']  = $user['role'];
            $_SESSION['user_email'] = $user['email'];

            // 5. Rehash si necessaire (mise a jour algo)
            if (password_needs_rehash($user['mot_de_passe'], PASSWORD_BCRYPT)) {
                $stmt = $this->pdo->prepare('UPDATE utilisateurs SET mot_de_passe = ? WHERE id = ?');
                $stmt->execute([password_hash($pass, PASSWORD_BCRYPT), $user['id']]);
            }

            header('Location: /dashboard');
            exit;

        } else {
            // Message identique : ne pas indiquer si c'est l'email ou le MDP
            $error = 'Email ou mot de passe incorrect';
        }
    }

    $this->render('auth/login', ['error' => $error ?? null]);
}
!
Message d'erreur volontairement ambigu. "Email ou mot de passe incorrect" ne precise pas lequel est faux. Si on disait "Email inconnu", un attaquant pourrait enumerer les comptes existants (user enumeration). Un message unique pour les deux cas bloque cette attaque.
!
password_needs_rehash(). Si le facteur de cout bcrypt est augmente dans le futur, cette fonction detecte que le hash existant utilise un facteur inferieur et le recalcule automatiquement a la prochaine connexion. Migration transparente pour les utilisateurs.

Etape 4

Session securisee et gardes

La session doit etre configuree avec les bonnes options de securite avant session_start(). Les fonctions de garde centralisent la logique de protection des pages.

config/session.php — demarrage securisePHP
<?php
// config/session.php — a inclure des le debut de chaque page

ini_set('session.cookie_httponly', '1');   // JS ne peut pas lire le cookie
ini_set('session.cookie_samesite', 'Strict'); // protection CSRF
ini_set('session.cookie_secure',   '1');   // HTTPS uniquement
ini_set('session.use_strict_mode', '1');   // session ID non devinable

session_start();

// Generer le token CSRF si pas encore fait
if (empty($_SESSION['csrf_token'])) {
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
}
app/Helpers/auth.php — gardes requireAuth() et requireRole()PHP
<?php
// app/Helpers/auth.php — fonctions de garde

// Verifier si l'utilisateur est connecte
function isLoggedIn(): bool {
    return !empty($_SESSION['user_id']);
}

// Forcer la connexion — redirige si pas connecte
function requireAuth(): void {
    if (!isLoggedIn()) {
        // Sauvegarder l'URL demandee pour y revenir apres connexion
        $_SESSION['redirect_after_login'] = $_SERVER['REQUEST_URI'];
        header('Location: /login');
        exit;
    }
}

// Forcer un role specifique
function requireRole(string $role): void {
    requireAuth();
    if ($_SESSION['user_role'] !== $role) {
        http_response_code(403);
        echo '<h1>403 Acces interdit</h1>';
        exit;
    }
}

// Recuperer l'utilisateur connecte
function currentUser(): ?array {
    return isLoggedIn() ? [
        'id'    => $_SESSION['user_id'],
        'nom'   => $_SESSION['user_nom'],
        'role'  => $_SESSION['user_role'],
        'email' => $_SESSION['user_email'],
    ] : null;
}

// Utilisation en debut de page protegee
requireAuth();              // redirige si non connecte
requireRole('admin');    // redirige 403 si pas admin
$user = currentUser();    // tableau infos user connecte
i
HttpOnly bloque le vol de session par XSS. L'option cookie_httponly rend le cookie de session inaccessible au JavaScript. Meme si une XSS passe, le cookie ne peut pas etre vole. SameSite=Strict bloque l'envoi du cookie depuis d'autres sites (CSRF).

Etape 5

Deconnexion

Une deconnexion complete efface les donnees de session cote serveur, detruit le fichier de session et supprime le cookie du navigateur. La deconnexion doit etre un POST, jamais un GET.

AuthController.php — logout() completPHP
<?php
public function logout(): void {

    // Verifier CSRF meme pour la deconnexion (prevent logout CSRF)
    $this->verifyCsrf($_POST['csrf_token'] ?? '');

    // 1. Vider les donnees de session
    session_unset();

    // 2. Detruire le fichier de session cote serveur
    session_destroy();

    // 3. Supprimer le cookie de session dans le navigateur
    if (ini_get('session.use_cookies')) {
        $params = session_get_cookie_params();
        setcookie(session_name(), '', time() - 42000,
            $params['path'], $params['domain'],
            $params['secure'], $params['httponly']
        );
    }

    // 4. Supprimer le cookie remember me si present
    if (isset($_COOKIE['remember_me'])) {
        setcookie('remember_me', '', time() - 3600, '/');
        // Supprimer aussi le token en BDD
        if (!empty($_SESSION['user_id'])) {
            $this->pdo->prepare('UPDATE utilisateurs SET remember_token = NULL WHERE id = ?')
                ->execute([$_SESSION['user_id']]);
        }
    }

    header('Location: /login'); exit;
}

// Dans la vue — bouton de deconnexion via formulaire POST
// Ne pas utiliser un lien <a href="/logout"> (GET) !
<form method="post" action="/logout">
    <input type="hidden" name="csrf_token" value="...">
    <button type="submit">Se deconnecter</button>
</form>
!
La deconnexion par lien GET est dangereuse. Un attaquant peut forger un lien <img src="/logout"> dans un email ou une page. Si la victime ouvre ce lien, elle est deconnectee. Utiliser un formulaire POST avec token CSRF protege contre ce "logout CSRF".

Etape 6

Roles et autorisation

Un systeme de roles hierarchiques permet de definir des niveaux d'acces. Un admin peut tout faire, un moderateur un sous-ensemble, un user simple encore moins. Plus souple que des roles binaires.

Roles hierarchiques — hasRole() et requireRoleMin()PHP
<?php
// Systeme de roles hierarchiques

const ROLES = ['user' => 1, 'moderateur' => 2, 'admin' => 3];

// Verifier si l'user a au moins le role demande
function hasRole(string $roleMin): bool {
    if (!isLoggedIn()) return false;
    $userLevel = ROLES[$_SESSION['user_role']] ?? 0;
    $minLevel  = ROLES[$roleMin] ?? 99;
    return $userLevel >= $minLevel;
}

// Proteger une page avec un niveau minimum
function requireRoleMin(string $role): void {
    requireAuth();
    if (!hasRole($role)) {
        http_response_code(403);
        $this->render('errors/403');
        exit;
    }
}

// Dans les vues : affichage conditionnel
<?php if (hasRole('admin')): ?>
    <a href="/admin">Administration</a>
<?php endif; ?>

// Dans le controller admin
requireRoleMin('moderateur');  // moderateur ET admin peuvent acceder
requireRoleMin('admin');        // admin uniquement
+
Toujours verifier les droits cote serveur. Masquer un bouton dans la vue ne suffit pas. Un utilisateur peut appeler directement /admin/supprimer/42. Chaque action sensible doit commencer par requireRole() ou requireRoleMin().

Etape 7

Remember me

Le "Se souvenir de moi" utilise un token aleatoire stocke dans un cookie et en BDD. On ne stocke jamais le token brut en BDD — seulement son hash SHA-256, pour limiter les dommages en cas de fuite de la BDD.

Remember me — generation et verification du tokenPHP
<?php
// Dans login() — apres connexion reussie

if (!empty($_POST['remember_me'])) {

    // Token aleatoire securise (64 chars hex)
    $token  = bin2hex(random_bytes(32));
    $expire = new DateTime('+30 days');

    // Stocker le hash du token en BDD (pas le token brut)
    $stmt = $this->pdo->prepare(
        'UPDATE utilisateurs SET remember_token = ?, token_expire_le = ? WHERE id = ?'
    );
    $stmt->execute([hash('sha256', $token), $expire->format('Y-m-d H:i:s'), $user['id']]);

    // Cookie avec le token brut + l'user_id
    setcookie('remember_me', $user['id'] . '|' . $token,
        time() + 30 * 24 * 3600,  // 30 jours
        '/', '', true, true   // secure, httponly
    );
}

// Au debut de chaque page — verifier le cookie remember me
if (!isLoggedIn() && isset($_COOKIE['remember_me'])) {
    [$userId, $token] = explode('|', $_COOKIE['remember_me'], 2);

    $stmt = $pdo->prepare(
        'SELECT * FROM utilisateurs WHERE id = ? AND remember_token = ? AND token_expire_le > NOW()'
    );
    $stmt->execute([(int)$userId, hash('sha256', $token)]);
    $user = $stmt->fetch();

    if ($user) {
        session_regenerate_id(true);
        $_SESSION['user_id']   = $user['id'];
        $_SESSION['user_role'] = $user['role'];
        // etc.
    }
}
!
Token brut dans le cookie, hash en BDD. Si la BDD est compromise, l'attaquant obtient le hash SHA-256 mais pas le token original. Sans le token brut, il ne peut pas forger le cookie. Le cookie contient userId|tokenBrut. On recompute le hash au moment de la verification.

Etape 8

Protection CSRF

Une attaque CSRF (Cross-Site Request Forgery) force le navigateur de la victime connectee a envoyer une requete a votre site. Le token CSRF, genere par le serveur et inconnu de l'attaquant, empeche ca.

Protection CSRF — generation, verification, formulairePHP
<?php
// Protection CSRF — dans le Controller de base

// Generation du token (dans config/session.php au demarrage)
if (empty($_SESSION['csrf_token'])) {
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
}

// Verification dans le Controller de base
protected function verifyCsrf(string $token): void {
    // hash_equals : comparaison en temps constant (anti-timing)
    if (!hash_equals($_SESSION['csrf_token'] ?? '', $token)) {
        http_response_code(419);
        exit('Token CSRF invalide');
    }
}

// Dans chaque formulaire HTML :
<input type="hidden" name="csrf_token"
       value="<?= htmlspecialchars($_SESSION['csrf_token']) ?>">

// En debut de chaque methode POST :
$this->verifyCsrf($_POST['csrf_token'] ?? '');

// Ce que ca protege :
// - Un site malveillant ne peut pas forger une requete POST
// - Car il ne connait pas le token stocke en session
// - Meme si l'utilisateur est connecte sur votre site
!
Utiliser hash_equals() pour comparer les tokens. Une comparaison classique $a === $b peut reveler la longueur du token par analyse du temps d'execution (timing attack). hash_equals() met toujours le meme temps independamment de la position de la difference.
