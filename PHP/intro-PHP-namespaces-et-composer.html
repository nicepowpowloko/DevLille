Namespaces
et Composer

Les namespaces organisent les classes pour eviter les conflits de noms. Composer est le gestionnaire de dependances de PHP : il installe les packages tiers et gere l'autoloading automatique de toutes vos classes.

namespaceuse / asPSR-4composer.jsonautoload
00
Concept

Pourquoi les namespaces

Sans namespaces, deux librairies qui definissent une classe User provoquent un Fatal error. Les namespaces agissent comme des dossiers pour les classes : ils permettent de distinguer App\Models\User de Symfony\Security\User.

Sans namespace — collision : class User { ... } <-- votre code class User { ... } <-- librairie tierce Fatal error: Cannot declare class User, already declared Avec namespace — coexistance : App\Models\User votre classe Symfony\Component\Security\User classe du framework Aucun conflit, noms entierement distincts
i
Norme PSR-4. PHP-FIG a defini la norme PSR-4 qui mappe les namespaces sur la structure de dossiers. App\Models\User correspond au fichier src/Models/User.php. Composer genere automatiquement un autoloader PSR-4 — plus aucun require_once manuel.
01
Etape 1

Declarer un namespace

src/Models/User.php — declaration du namespacePHP
<?php
// PREMIERE ligne apres <?php obligatoirement
namespace App\Models;

class User {
    public function __construct(
        public string $nom,
        public string $email,
    ) {}
}
// Nom complet (FQCN) : App\Models\User
src/Services/UserService.php — importer une classePHP
<?php
namespace App\Services;

// Importer une classe par son FQCN
use App\Models\User;

class UserService {
    public function creer(string $nom, string $email): User {
        // "User" resolu grace au use ci-dessus
        return new User($nom, $email);
    }
}

// Sans use, il faudrait ecrire le FQCN complet :
// return new App\Models\User($nom, $email);

// Classes PHP globales dans un namespace : prefixer avec \
$dt = new \DateTime();
// Sans \ : PHP cherche App\Services\DateTime (inexistant)
!
Classes globales dans un namespace. A l'interieur d'un namespace, les classes PHP natives (DateTime, Exception, PDO, InvalidArgumentException) doivent etre prefixees par \ ou importees explicitement avec use DateTime;. Sans ca, PHP les cherche dans le namespace courant.
02
Etape 2

use et alias

use — import, alias et import groupePHP
<?php
namespace App\Http\Controllers;

// Import simple
use App\Models\User;
use App\Models\Produit;
use App\Services\UserService;

// Alias : renommer pour eviter les conflits ou raccourcir
use App\Models\User          as AppUser;
use Symfony\Security\User  as SymfonyUser;

// Import groupe PHP 7+ : meme prefixe de namespace
use App\Models\{User, Produit, Categorie};

// Importer une fonction ou une constante
use function App\Helpers\formatPrix;
use const    App\Config\VERSION;

// Utilisation dans la classe
class UserController {
    public function store(): User {
        // "User" = App\Models\User grace au use
        return (new UserService())->creer('Alice', 'alice@ex.com');
    }
}
!
Toujours importer en haut du fichier. Les declarations use vont apres le namespace et avant toute declaration de classe. Elles ne font que creer des raccourcis : elles ne chargent pas les fichiers (c'est le role de l'autoloader).
03
Etape 3

Autoloading PSR-4

Sans autoloader, chaque classe necessite un require_once. L'autoloader PSR-4 de Composer charge automatiquement chaque classe au moment ou on l'utilise, en suivant la correspondance namespace → dossier.

Correspondance namespace vers fichier (PSR-4)Structure
// Regle PSR-4 definie dans composer.json :
// "App\\" => "src/"

// Namespace              Fichier physique
App\Models\User        -> src/Models/User.php
App\Services\Mailer    -> src/Services/Mailer.php
App\Http\Router         -> src/Http/Router.php
App\Http\Middleware\Auth  -> src/Http/Middleware/Auth.php

projet/
  src/
    Models/
      User.php          <-- namespace App\Models;
      Produit.php       <-- namespace App\Models;
    Services/
      Mailer.php        <-- namespace App\Services;
    Http/
      Router.php        <-- namespace App\Http;
      Middleware/
        Auth.php        <-- namespace App\Http\Middleware;
  vendor/               <-- packages Composer
  composer.json
  index.php
Sans vs avec autoloaderPHP
<?php
// Avant Composer : require_once pour chaque fichier
require_once 'src/Models/User.php';
require_once 'src/Models/Produit.php';
require_once 'src/Services/Mailer.php';
// ... un require par classe : difficile a maintenir

// Avec Composer : un seul require
require_once __DIR__ . 'vendor/autoload.php';

// Toutes les classes du projet et des packages sont
// disponibles immediatement, chargees a la demande.

use App\Models\User;
$u = new User('Alice', 'alice@ex.com');
// Composer charge src/Models/User.php automatiquement
+
Principe "lazy loading". L'autoloader ne charge les fichiers qu'au moment de la premiere utilisation de la classe. Si Mailer n'est jamais instancie dans une requete, son fichier n'est jamais lu. C'est plus efficace que des dizaines de require_once inconditionnels.

05
Etape 5

composer.json

Le fichier composer.json est la configuration centrale du projet. Il liste les dependances, definit l'autoloading PSR-4 et peut contenir des scripts.

composer.json — configuration completeComplet
{
    "name": "monentreprise/monprojet",
    "description": "Application de gestion",
    "type": "project",
    "require": {
        "php": ">=8.1",
        "vlucas/phpdotenv": "^5.6",
        "phpmailer/phpmailer": "^6.9"
    },
    "require-dev": {
        "phpunit/phpunit": "^11.0"
    },
    "autoload": {
        "psr-4": {
            "App\\": "src/"
        }
    },
    "autoload-dev": {
        "psr-4": {
            "Tests\\": "tests/"
        }
    },
    "scripts": {
        "test": "phpunit"
    }
}
CleRole
"require"Dependances de production — installees partout
"require-dev"Dependances de developpement — tests, debug, etc.
"autoload"Mapping PSR-4 pour votre code (namespace => dossier)
"autoload-dev"Mapping PSR-4 pour les tests
"scripts"Commandes shortcut : composer test, composer serve...
composer.lockGenere auto : versions exactes installees (a versionner)
!
Ne jamais versionner vendor/. Le dossier vendor peut peser plusieurs centaines de Mo. Ajouter vendor/ dans le .gitignore. En revanche, versionner composer.lock — il garantit que tous les devs installent exactement les memes versions.

Etape 6

Utiliser un package — phpdotenv

Installer phpdotenvTerminal
# Ajouter phpdotenv dans require
composer require vlucas/phpdotenv
# Telecharge dans vendor/ et met a jour composer.json + composer.lock

# Ajouter une dependance de dev
composer require --dev phpunit/phpunit
.env — variables sensibles hors du codeConfig
# .env (a la racine du projet, ne pas versionner)
APP_ENV=development
APP_SECRET=monSecretAleatoire
DB_HOST=localhost
DB_PORT=3306
DB_NAME=boutique
DB_USER=appuser
DB_PASS=motdepasse
public/index.php — autoloader + .env + vos classesPHP
<?php
// public/index.php — point d'entree unique
require_once __DIR__ . '/../vendor/autoload.php';

// 1. Charger les variables .env
use Dotenv\Dotenv;
$dotenv = Dotenv::createImmutable(dirname(__DIR__));
$dotenv->load();

// 2. Utiliser les variables d'environnement
$host   = $_ENV['DB_HOST'];    // "localhost"
$dbName = $_ENV['DB_NAME'];    // "boutique"

// 3. Utiliser vos propres classes (autoloader PSR-4)
use App\Services\UserService;
use App\Http\Router;

$service = new UserService();
// Composer charge src/Services/UserService.php automatiquement
// Pas de require_once manuel !
+
Ne jamais mettre les secrets dans le code. Les mots de passe, cles API, et configurations sensibles vont dans .env (non versionne). On versionne .env.example avec des valeurs fictives comme modele pour les autres developpeurs.

Reference

Commandes Composer essentielles

Commandes Composer — reference completeTerminal
# GESTION DES DEPENDANCES

# Installer depuis composer.lock (production, reproductible)
composer install

# Mettre a jour toutes les dependances (dev uniquement)
composer update

# Ajouter un package
composer require phpmailer/phpmailer
composer require symfony/var-dumper
composer require --dev phpunit/phpunit

# Supprimer un package
composer remove vlucas/phpdotenv

# AUTOLOADER

# Regenerer apres modification de la section "autoload"
composer dump-autoload
composer dump-autoload --optimize   # plus rapide en prod

# INSPECTION

# Lister les packages installes
composer show
composer show vlucas/phpdotenv  # detail d'un package

# Mises a jour disponibles
composer outdated

# Chercher un package sur packagist.org
composer search "pdf generator"

# Valider le composer.json
composer validate
!
install vs update en production. En production, utiliser uniquement composer install — il lit composer.lock et installe exactement les versions testees. composer update peut installer des versions plus recentes qui cassent l'application : ne l'utiliser qu'en developpement.

public/index.php — point d'entreePHP
<?php
// public/index.php — point d'entree unique de l'application
require_once dirname(__DIR__) . '/vendor/autoload.php';

// Charger l'environnement

OK
Mise en place en 4 etapes : (1) composer init + configurer PSR-4 (2) composer install (3) require vendor/autoload.php dans index.php (4) chaque classe PHP = son propre fichier avec le namespace correspondant a son dossier.
