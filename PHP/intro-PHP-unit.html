Tests unitaires
PHPUnit

PHPUnit est le framework de tests unitaires standard de PHP. Un test unitaire verifie qu'une unite de code (une methode, une fonction) produit le bon resultat dans des conditions donnees.

00
Concept

Pourquoi ecrire des tests

Les tests automatises detectent les regressions avant que les utilisateurs ne les trouvent. Un test ecrit une fois protege indefiniment contre les bugs futurs.

Sans testsAvec tests
Modifier du code = peur de casser quelque choseModifier du code = confiance (les tests passent)
Decouvrir les bugs en productionDecouvrir les bugs sur le poste du dev
Refactoring risqueRefactoring serein (meme comportement garanti)
Documentation obsoleteTests = documentation executable toujours a jour
Debugger a la main avec var_dumpFeedback instantane en quelques secondes
i
Test unitaire vs test d'integration. Un test unitaire teste une seule methode en isolation (sans BDD, sans reseau, sans fichiers). Un test d'integration teste plusieurs composants ensemble. On commence par les tests unitaires : rapides, fiables, sans dependances.

02
Etape 2

Premier test — pattern AAA

Chaque test suit le pattern Arrange / Act / Assert (AAA) : preparer les donnees, executer le code, verifier le resultat.

src/Calculatrice.php — classe a testerPHP
<?php
// src/Calculatrice.php — classe a tester
class Calculatrice {

    public function additionner(float $a, float $b): float {
        return $a + $b;
    }

    public function diviser(float $a, float $b): float {
        if ($b === 0.0) {
            throw new InvalidArgumentException('Division par zero');
        }
        return $a / $b;
    }
}
tests/CalculatriceTest.php — premier testPHP
<?php
// tests/CalculatriceTest.php
use PHPUnit\Framework\TestCase;

class CalculatriceTest extends TestCase {

    private Calculatrice $calc;

    // setUp() est appele avant CHAQUE methode de test
    protected function setUp(): void {
        $this->calc = new Calculatrice();
    }

    // Methode de test : commence par "test"
    public function testAdditionnerDeuxNombresPositifs(): void {
        // Arrange — preparer les donnees
        $a = 3.0; $b = 4.0;

        // Act — executer le code
        $result = $this->calc->additionner($a, $b);

        // Assert — verifier le resultat
        $this->assertSame(7.0, $result);
    }

    public function testAdditionnerNegatifEtPositif(): void {
        $this->assertSame(1.0, $this->calc->additionner(-2.0, 3.0));
    }

    public function testAdditionnerZero(): void {
        $this->assertSame(5.0, $this->calc->additionner(5.0, 0.0));
    }
}
Lancer les testsTerminal
# Lancer tous les tests
./vendor/bin/phpunit

# Lancer un fichier specifique
./vendor/bin/phpunit tests/CalculatriceTest.php

# Lancer une methode specifique
./vendor/bin/phpunit --filter testAdditionnerDeuxNombresPositifs
PHPUnit 11.x by Sebastian Bergmann and contributors. ... 3 / 3 (100%) Time: 00:00.012, Memory: 4.00 MB OK (3 tests, 3 assertions)
+
setUp() est cle. La methode setUp() est appelee avant chaque test, creant un objet frais. Cela garantit que chaque test part d'un etat propre et ne peut pas etre affecte par les effets de bord d'un test precedent.

Etape 3

Assertions

PHPUnit propose des dizaines d'assertions. La plus importante : assertSame qui utilise ===. Eviter assertEquals qui utilise == et peut masquer des bugs de type.

Assertions PHPUnit — reference completePHP
<?php
// Assertions d'egalite
$this->assertSame(42, $result);            // egalite stricte (===)
$this->assertEquals('42', 42);         // egalite loose (==) — utiliser assertSame en priorite
$this->assertNotSame(0, $result);         // non egal strict

// Assertions booleennes
$this->assertTrue($bool);                  // doit etre true
$this->assertFalse($bool);                 // doit etre false

// Assertions sur les tableaux
$this->assertCount(3, $array);             // nombre d'elements
$this->assertContains('Alice', $array);    // contient la valeur
$this->assertArrayHasKey('nom', $array); // cle presente

// Assertions sur les chaines
$this->assertStringContainsString('PHP', $str);  // contient la sous-chaine
$this->assertStringStartsWith('Hello', $str); // commence par
$this->assertMatchesRegularExpression('#^\d+$#', $str);

// Assertions sur les types
$this->assertIsInt($val);
$this->assertIsString($val);
$this->assertIsArray($val);
$this->assertNull($val);
$this->assertNotNull($val);
$this->assertInstanceOf(Produit::class, $obj);

// Assertion avec message personnalise
$this->assertSame(7.0, $result, '3 + 4 devrait valoir 7');

// assertSame vs assertEquals : TOUJOURS preferez assertSame
$this->assertSame(0, false);   // ECHEC : types differents
$this->assertEquals(0, false); // PASSE : loose comparison
!
assertSame plutot que assertEquals. assertEquals(0, false) passe car 0 == false en PHP. assertSame(0, false) echoue correctement car 0 !== false. Les bugs de type sont reels en PHP : preferez toujours la comparaison stricte dans les tests.

Etape 4

Tester les exceptions

Tester qu'une exception est bien lancee est aussi important que tester le bon resultat. expectException() doit etre appele avant le code qui lance l'exception.

Tester les exceptionsPHP
<?php
public function testDiviserParZeroLanceException(): void {
    // Declarer que la prochaine operation doit lancer une exception
    $this->expectException(InvalidArgumentException::class);

    // Cette ligne doit lancer l'exception
    $this->calc->diviser(10, 0);
    // Si l'exception n'est pas lancee : le test echoue
}

public function testDiviserParZeroMessageCorrect(): void {
    $this->expectException(InvalidArgumentException::class);
    $this->expectExceptionMessage('Division par zero');
    $this->expectExceptionCode(0);

    $this->calc->diviser(10, 0);
}

// Alternative avec try/catch explicite
public function testDiviserParZeroAvecCatch(): void {
    try {
        $this->calc->diviser(10, 0);
        $this->fail('Une exception aurait du etre lancee');
    } catch (InvalidArgumentException $e) {
        $this->assertStringContainsString('zero', $e->getMessage());
    }
}
i
$this->fail() force l'echec. Dans le pattern try/catch, si le code ne lance pas d'exception, on atteint la ligne $this->fail() qui fait echouer le test avec un message clair. Sans ca, le test passerait silencieusement alors que le comportement attendu ne s'est pas produit.

Etape 5

Data Providers

Un data provider permet de lancer le meme test avec plusieurs jeux de donnees. On ecrit la logique de test une seule fois et on la nourrit avec toutes les combinaisons a couvrir.

Data Provider — #[DataProvider]PHP
<?php
use PHPUnit\Framework\Attributes\DataProvider;

class CalculatriceTest extends TestCase {

    // Le data provider fournit les jeux de donnees
    public static function additionDataProvider(): array {
        return [
            // [a, b, resultats_attendu, description]
            'positifs'             => [3.0,  4.0,  7.0],
            'negatif et positif'   => [-2.0, 3.0,  1.0],
            'deux negatifs'       => [-1.0, -1.0, -2.0],
            'avec zero'           => [5.0,  0.0,  5.0],
            'decimaux'            => [1.5,  2.5,  4.0],
        ];
    }

    // PHPUnit execute ce test UNE FOIS PAR ligne du data provider
    #[DataProvider('additionDataProvider')]
    public function testAdditionner(float $a, float $b, float $attendu): void {
        $this->assertSame($attendu, $this->calc->additionner($a, $b));
    }
}
..... 5 / 5 (100%) CalculatriceTest::testAdditionner with data set "positifs" (3, 4, 7) CalculatriceTest::testAdditionner with data set "negatif et positif" (-2, 3, 1) ... OK (5 tests, 5 assertions)
!
Nommer les datasets avec des cles string. Au lieu de tableaux numerotes, utiliser des cles descriptives ("positifs", "negatif et positif"). Quand un test echoue, PHPUnit affiche le nom du dataset ce qui localise immediatement quel cas pose probleme.

Etape 6

Mocks et stubs

Un mock remplace une dependance reelle (BDD, mailer, API) par un simulacre. Le test reste unitaire : rapide, reproductible, sans effets de bord.

Mocks — tester sans dependances reellesPHP
<?php
// Un mock remplace une dependance reelle par un simulacre controlable
// Exemple : ProduitService depend d'un ProduitRepository

class ProduitServiceTest extends TestCase {

    public function testCalculerStockTotal(): void {
        // Creer un mock de ProduitRepository
        $mockRepo = $this->createMock(ProduitRepository::class);

        // Configurer : findAll() doit retourner ce tableau
        $mockRepo->method('findAll')
              ->willReturn([
                  ['nom' => 'T-shirt', 'stock' => 50],
                  ['nom' => 'Jean',    'stock' => 30],
              ]);

        // Injecter le mock dans le service
        $service = new ProduitService($mockRepo);

        // Tester sans toucher la BDD
        $this->assertSame(80, $service->calculerStockTotal());
    }

    public function testEnvoyerEmailAppelleMailer(): void {
        $mockMailer = $this->createMock(MailerInterface::class);

        // Verifier qu'envoyer() est appele EXACTEMENT UNE FOIS
        $mockMailer->expects($this->once())
               ->method('envoyer')
               ->with('alice@ex.com', $this->stringContains('Bienvenue'));

        $service = new UserService($mockMailer);
        $service->inscrire('Alice', 'alice@ex.com');
        // PHPUnit verifie automatiquement que once() a ete respecte
    }
}
i
Pour mocker une classe, elle doit etre injectable. Si ProduitService cree lui-meme son ProduitRepository avec new, on ne peut pas le remplacer par un mock. Il faut injecter la dependance via le constructeur (injection de dependances) pour pouvoir la substituer dans les tests.

Etape 7

Tester avec PDO / SQLite

Pour tester du code avec PDO sans toucher la vraie BDD, on utilise SQLite en memoire : instantane, sans configuration, reinitialisee a chaque test.

Tester un Model PDO avec SQLite en memoirePHP
<?php
// Option 1 : base de donnees SQLite en memoire pour les tests
// Rapide, sans configuration, reinitialisee a chaque test

class ProduitModelTest extends TestCase {

    private PDO $pdo;
    private ProduitModel $model;

    protected function setUp(): void {
        // SQLite en memoire — disparait a la fin du test
        $this->pdo = new PDO('sqlite::memory:');
        $this->pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

        // Creer le schema de test
        $this->pdo->exec('
            CREATE TABLE produits (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                nom TEXT NOT NULL,
                prix REAL NOT NULL,
                stock INTEGER DEFAULT 0
            )
        ');

        // Donnees de test
        $this->pdo->exec('INSERT INTO produits (nom, prix, stock) VALUES
            ('T-shirt', 19.99, 50),
            ('Jean', 49.99, 0)');

        $this->model = new ProduitModel($this->pdo);
    }

    public function testFindAllRetourneTousLesProduits(): void {
        $produits = $this->model->findAll();
        $this->assertCount(2, $produits);
        $this->assertSame('T-shirt', $produits[0]['nom']);
    }

    public function testCreateAjouteUnProduit(): void {
        $id = $this->model->create(['nom' => 'Veste', 'prix' => 89.99, 'stock' => 10]);
        $this->assertIsInt($id);
        $this->assertGreaterThan(0, $id);

        // Verifier que le produit est bien en BDD
        $produit = $this->model->findById($id);
        $this->assertNotNull($produit);
        $this->assertSame('Veste', $produit['nom']);
    }
}
+
SQLite en memoire = tests BDD sans BDD. new PDO("sqlite::memory:") cree une BDD temporaire en RAM. Elle est compatible avec la majorite du SQL standard. Le test cree le schema, insere des donnees, execute le code, verifie le resultat. Chaque test repart d'une BDD vierge.

Coverage et configuration

La couverture de code (code coverage) mesure le pourcentage de lignes executees par les tests. Un taux de 80% est un bon objectif : viser 100% peut mener a des tests artificiels sans valeur.

Generer le rapport de couvertureTerminal
# Generer le rapport de couverture (necessite Xdebug ou PCOV)
./vendor/bin/phpunit --coverage-text

# Rapport HTML dans coverage/
./vendor/bin/phpunit --coverage-html coverage/

# Installer Xdebug pour la couverture (Linux)
sudo apt install php-xdebug

# Ou PCOV (plus rapide que Xdebug)
composer require --dev pcov/clobber
phpunit.xml — configuration coverageXML
<!-- Ajouter dans phpunit.xml -->
<coverage>
    <report>
        <html outputDirectory="coverage" lowUpperBound="50" highLowerBound="90"/>
        <text outputFile="php://stdout" showUncoveredFiles="true"/>
    </report>
</coverage>
Code Coverage Report: Calculatrice Methods: 100.00% (2/2) Lines: 100.00% (5/5) ProduitModel Methods: 75.00% (3/4) Lines: 83.33% (10/12) Summary: Classes: 50.00%, Methods: 85.71%, Lines: 90.00%
!
La couverture ne garantit pas la qualite. 100% de lignes couvertes ne signifie pas que tous les comportements sont testes. Un test qui appelle une methode sans faire d'assertion contribue a la couverture mais ne teste rien. La couverture est un indicateur, pas une garantie.

Synthese

TDD et cycle de vie des tests

Le TDD (Test-Driven Development) inverse l'ordre : on ecrit le test avant le code. Cycle Red → Green → Refactor. Les tests guident la conception du code.

Cycle TDD — Red / Green / RefactorPHP
<?php
// TDD : Test-Driven Development
// Cycle : RED (test echoue) -> GREEN (code minimal) -> REFACTOR

// ETAPE 1 : RED — ecrire le test d'abord (la classe n'existe pas encore)
public function testValiderEmailCorrect(): void {
    $validator = new EmailValidator();
    $this->assertTrue($validator->isValid('alice@example.com'));
}

public function testValiderEmailSansAt(): void {
    $validator = new EmailValidator();
    $this->assertFalse($validator->isValid('pasdetat'));
}

// ETAPE 2 : GREEN — implementation minimale pour faire passer les tests
class EmailValidator {
    public function isValid(string $email): bool {
        return (bool)filter_var($email, FILTER_VALIDATE_EMAIL);
    }
}

// ETAPE 3 : REFACTOR — ameliorer sans casser les tests
class EmailValidator {
    const int MAX_LENGTH = 254;

    public function isValid(string $email): bool {
        if (strlen($email) > self::MAX_LENGTH) return false;
        return (bool)filter_var($email, FILTER_VALIDATE_EMAIL);
    }
    // Les tests passent toujours apres le refactoring
}
Methode de cycle de vieQuand appelee
setUpBeforeClass()Une fois avant toute la classe de test (static)
setUp()Avant chaque methode de test
tearDown()Apres chaque methode de test (nettoyage)
tearDownAfterClass()Une fois apres toute la classe (static)
OK
Recap PHPUnit : installer avec Composer (--dev), etendre TestCase, methodes commencent par test, pattern Arrange/Act/Assert, assertSame pour la comparaison stricte, data providers pour les jeux de donnees, mocks pour les dependances, SQLite en memoire pour PDO.
