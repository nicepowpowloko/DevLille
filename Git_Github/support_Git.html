01

C'est quoi Git ?

Fondamentaux

Git est un système de contrôle de version (Version Control System). Il enregistre chaque modification de ton code dans un historique, te permet de revenir en arrière, de travailler en équipe sans écraser le travail des autres, et de gérer plusieurs fonctionnalités en parallèle.

Analogie : imagine Git comme un jeu vidéo où tu peux créer des sauvegardes à n'importe quel moment. Si tu fais une erreur, tu reviens à la sauvegarde précédente. GitHub est le cloud où tu stockes ces sauvegardes pour les partager avec ton équipe.
Dépôt local
Le dossier .git caché dans ton projet. Contient tout l'historique en local sur ta machine.
Dépôt distant
Hébergé sur GitHub, GitLab ou Bitbucket. Permet de sauvegarder et partager ton code en ligne.
Commit
Une sauvegarde de l'état de tes fichiers à un instant T, avec un message décrivant les changements.
Branche
Une ligne de développement indépendante. On crée une branche pour chaque nouvelle fonctionnalité ou correction.

02

Installation & Configuration

Avant toute chose, vérifie si Git est déjà installé puis configure ton identité. Git utilise ton nom et email pour signer chaque commit.

terminal 
# Vérifier la version installée
git --version
# git version 2.44.0

# ─── Configuration globale (une seule fois) ───
git config --global user.name  "Prénom Nom"
git config --global user.email "ton@email.com"

# Définir VS Code comme éditeur par défaut
git config --global core.editor "code --wait"

# Vérifier la configuration
git config --list
🍏
Sur Mac : Git est souvent déjà installé avec Xcode Command Line Tools. Sinon : brew install git. Sur Windows : télécharge Git for Windows qui inclut Git Bash.
terminal — initialiser un projet 
# Dans ton dossier de projet
cd mon-projet
git init
# Initialized empty Git repository in ./mon-projet/.git/

# OU cloner un repo existant depuis GitHub
git clone https://github.com/user/repo.git
git clone https://github.com/user/repo.git mon-dossier
                                              ↑ nom optionnel du dossier local
03

Workflow local

Les 4 commandes clés

Le cycle quotidien avec Git tourne autour de 4 commandes que tu utiliseras des dizaines de fois par jour.

1
git status — vérifier l'état
Toujours commencer par là. Montre quels fichiers ont été modifiés, ajoutés ou supprimés.
2
git add — préparer les fichiers
Ajoute les fichiers dans la zone de staging (les fichiers que tu veux inclure dans le prochain commit).
3
git commit — sauvegarder
Crée un point de sauvegarde avec un message descriptif. C'est la photo de l'état de ton code.
4
git push — envoyer sur GitHub
Envoie tes commits locaux sur le dépôt distant (GitHub). Partage ton travail.
terminal — cycle quotidien complet 
# 1. Vérifier ce qui a changé
git status
# On branch main
# Changes not staged for commit:
#   modified:   index.html
# Untracked files:
#   style.css

# 2a. Ajouter un fichier spécifique
git add index.html

# 2b. Ajouter TOUS les fichiers modifiés
git add .

# 3. Créer un commit avec un message
git commit -m "feat: ajout formulaire de contact"

# 4. Envoyer sur GitHub
git push
# OU la première fois sur une nouvelle branche :
git push -u origin main
Bonne pratique : ne jamais faire git add . sans avoir fait git status avant ! Tu risques d'ajouter des fichiers non voulus (mots de passe, node_modules…). Utilise un .gitignore — on y reviendra.
04

Les commits

Un bon message de commit se lit comme une phrase à l'impératif qui complète : "Si appliqué, ce commit va…". La convention Conventional Commits est très utilisée en entreprise.

convention de message — Conventional Commits 
# Format : type(scope): description courte

feat: ajouter la page de connexion
fix: corriger le bug d'affichage sur mobile
style: reformater le CSS du header
docs: mettre à jour le README
refactor: simplifier la fonction fetchUser()
chore: mettre à jour les dépendances npm
test: ajouter les tests unitaires du panier

# Exemple avec scope :
feat(auth): ajouter la validation JWT
fix(cart): corriger le calcul du total avec réduction
terminal — commandes utiles sur les commits 
# Modifier le DERNIER commit (message ou fichiers)
git commit --amend -m "nouveau message"

# Annuler le dernier commit (garder les fichiers modifiés)
git reset --soft HEAD~1

# Annuler le dernier commit (supprimer les modifications)
git reset --hard HEAD~1
             ↑ DANGER : perte définitive des modifications !

# Voir les différences avant de committer
git diff
git diff --staged  # fichiers déjà dans le staging
05

Historique & log

terminal — explorer l'historique 
# Voir tous les commits
git log

# Version compacte (une ligne par commit) ← le plus utilisé
git log --oneline
# a3f2c1b feat: ajout page accueil
# 9d8e7f6 fix: correction bug formulaire
# 1a2b3c4 init: structure du projet

# Voir le log avec graphe des branches
git log --oneline --graph --all

# Voir les modifications d'un commit spécifique
git show a3f2c1b

# Revenir à un état précédent (lecture seule)
git checkout a3f2c1b
# Revenir à la branche principale
git checkout main
06

Créer & naviguer dans les branches

Indispensable

Les branches permettent de travailler sur une fonctionnalité sans toucher au code stable. En équipe, chaque développeur travaille sur sa propre branche.

// Schéma de branches
terminal — gestion des branches 
# Voir toutes les branches (locale)
git branch
# * main          ← la branche active (étoile)
#   feature/login

# Créer une branche
git branch feature/ma-fonctionnalite

# Basculer sur une branche (nouvelle syntaxe recommandée)
git switch feature/ma-fonctionnalite

# Créer ET basculer en une seule commande ← le plus utilisé
git switch -c feature/nouvelle-page
# ancienne syntaxe équivalente :
git checkout -b feature/nouvelle-page

# Renommer une branche
git branch -m ancien-nom nouveau-nom

# Supprimer une branche (après merge)
git branch -d feature/ma-fonctionnalite
Convention de nommage : utilise des préfixes clairs — feature/nom pour une nouvelle fonctionnalité, fix/nom pour une correction de bug, hotfix/nom pour une correction urgente en production.
07

Merge & résolution de conflits

Quand tu as fini sur ta branche, tu la fusionne (merge) dans main. Si deux personnes ont modifié le même endroit, Git crée un conflit que tu dois résoudre manuellement.

terminal — merge d'une branche 
# 1. Se placer sur la branche de destination
git switch main

# 2. Fusionner la branche feature
git merge feature/login
# Merge made by the 'ort' strategy.
# index.html | 12 ++++++++++
# style.css  |  8 ++++----

# 3. Supprimer la branche mergée (bonne pratique)
git branch -d feature/login
résolution d'un conflit 
# Git t'indique un conflit :
CONFLICT (content): Merge conflict in index.html

# Dans le fichier en conflit, Git ajoute des marqueurs :
<<<<<<< HEAD
<h1>Bienvenue</h1>        ← ta version (HEAD = branche actuelle)
=======
<h1>Bienvenue sur le site</h1>  ← version de l'autre branche
>>>>>>> feature/header

# 1. Modifie le fichier : garde une version, supprime les marqueurs
<h1>Bienvenue sur le site</h1>

# 2. Marquer le conflit comme résolu
git add index.html

# 3. Finaliser le merge
git commit -m "merge: résolution conflit header"
VS Code affiche les conflits avec des boutons cliquables : "Accept Current Change", "Accept Incoming Change", "Accept Both". C'est beaucoup plus pratique que d'éditer manuellement les marqueurs.
08

Remote, Push & Pull

GitHub

Le remote est le lien entre ton dépôt local et GitHub. Par convention, il s'appelle origin.

terminal — relier son projet à GitHub 
# Voir les remotes configurés
git remote -v
# origin  https://github.com/user/repo.git (fetch)
# origin  https://github.com/user/repo.git (push)

# Relier un projet local à GitHub (après git init)
git remote add origin https://github.com/user/repo.git

# Premier push (crée la branche main sur GitHub)
git push -u origin main

# Pushs suivants (plus besoin de -u)
git push

# Récupérer les mises à jour de GitHub
git pull
# équivalent à : git fetch + git merge

# Voir les branches distantes
git branch -a
Toujours faire git pull avant de commencer à coder quand on travaille en équipe. Cela évite de travailler sur du code obsolète et limite les conflits.
09

Collaboration & Pull Requests

En entreprise, on ne pousse jamais directement sur main. On crée une Pull Request (PR) sur GitHub pour proposer ses changements, permettre une code review, et déclencher des tests automatiques avant de merger.

// Workflow Git Flow simplifié (équipe)
1
Cloner / Pull la dernière version de main
git clone … ou git pull origin main
2
Créer une branche pour ta tâche
git switch -c feature/ma-tache
3
Coder, committer régulièrement
git add . → git commit -m "feat: …"
4
Pousser la branche sur GitHub
git push -u origin feature/ma-tache
5
Ouvrir une Pull Request sur GitHub
Sur github.com → bouton "Compare & pull request" → décrire les changements → assigner un reviewer.
6
Code Review & Merge
Un collègue relit le code, approuve et merge la PR. La branche feature est supprimée.
terminal — commandes avancées utiles 
# Mettre son travail en cours de côté (sans committer)
git stash
git stash pop# récupérer le travail mis de côté
git stash list# voir tous les stash

# Récupérer un seul commit d'une autre branche
git cherry-pick a3f2c1b

# Réécrire l'historique proprement (rebase)
git rebase main      # rejouer ses commits par-dessus main
# Ne jamais rebaser une branche partagée !
10

.gitignore

Le fichier .gitignore liste les fichiers et dossiers que Git doit ignorer — ne jamais committer. Cela protège les données sensibles et évite les fichiers inutiles dans le dépôt.

.gitignore — exemple complet 
# ── Dépendances ──
node_modules/
vendor/

# ── Variables d'environnement (TRÈS IMPORTANT) ──
.env
.env.local
.env.production

# ── Builds / dist ──
dist/
build/
.next/

# ── Éditeurs ──
.vscode/
.idea/
*.swp

# ── OS ──
.DS_Store   # Mac
Thumbs.db   # Windows

# ── Logs ──
*.log
npm-debug.log*
