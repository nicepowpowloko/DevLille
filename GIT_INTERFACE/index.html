6 Inviter un collaborateur

Pour que ton équipier puisse pusher sur ton repo, tu dois l'inviter. Sans ça, il peut seulement lire.

1
Aller dans Settings du repo

Onglet Settings en haut de la page du repo (pas le Settings de ton compte !)

2
Collaborators dans le menu gauche

Settings → Collaborators → cliquer sur "Add people"

3
Chercher l'équipier par son pseudo GitHub

Taper le pseudo GitHub de Bob → le sélectionner → "Add [nom] to this repository"

4
Bob reçoit un email d'invitation

Il doit cliquer sur "Accept invitation" dans l'email, ou aller sur github.com/notifications. Après ça, il peut push.

Attention Le Settings dans la barre de navigation du repo ≠ le Settings de ton compte GitHub. Pour inviter un collaborateur : Settings du repo, pas de ton profil.

7 Comprendre une Pull Request

Une Pull Request (PR) c'est une demande formelle de fusionner une branche dans main. C'est le cœur du travail en équipe sur GitHub.

Ce que permet une PR

L'équipier voit exactement ce qui va changer

On peut commenter des lignes spécifiques

On peut demander des modifications avant de valider

GitHub vérifie les conflits automatiquement

Vocabulaire PR

base : la branche cible (souvent main)

compare : ta branche avec tes changements

reviewer : la personne qui doit valider

merge : fusionner après validation

10 Merger la Pull Request

1
Cliquer "Merge pull request"

Le bouton vert en bas de la PR. GitHub confirme le merge.

2
Confirmer avec "Confirm merge"

GitHub demande une confirmation. La branche est fusionnée dans main.

3
Supprimer la branche — "Delete branch"

GitHub propose directement. Cliquer dessus pour garder le repo propre.

4
Les deux font git pull origin main

Pour récupérer le merge en local sur leur machine.

Après le merge, la PR passe en "Merged" (violet) Elle reste consultable dans l'historique des PR. On peut voir toute l'historique des discussions et décisions de l'équipe.

11 Les Issues — gérer les tâches et bugs

Les Issues servent à lister les tâches à faire, signaler des bugs, ou noter des idées. C'est le mini-Trello de GitHub.

Comment utiliser les Issues en duo

1
Onglet Issues → "New issue"

Donner un titre clair + description. Assigner à Alice ou Bob selon qui s'en occupe.

2
Ajouter des labels

bug feature documentation — Pour filtrer et prioriser.

3
Fermer l'issue via un commit ou une PR

Dans le message du commit, écrire Closes #12 → l'issue #12 se ferme automatiquement au merge.

Astuce pro Dans le message d'une PR ou d'un commit, écrire Closes #5, Fixes #3 ou Resolves #8 ferme automatiquement l'issue correspondante au moment du merge. Très pratique pour garder les issues synchronisées avec le code.

12 Raccourcis et astuces interface

Raccourcis clavier GitHub

/ — Focus sur la barre de recherche

T — Chercher un fichier dans le repo

L — Aller à un numéro de ligne

B — Ouvrir la vue "Blame" (qui a écrit quelle ligne)

? — Voir tous les raccourcis disponibles

. (point) — Ouvrir le repo dans VS Code en ligne !

URL utiles à connaître

/commits/main → historique commits

/branches → toutes les branches

/pulls → toutes les PR

/issues → toutes les issues

/settings/access → inviter collaborateurs

/network → graphe des branches

Le point (.) — VS Code dans le navigateur Sur n'importe quel repo GitHub, appuyer sur la touche . (point) ouvre automatiquement un VS Code en ligne dans le navigateur. On peut lire et naviguer dans le code sans rien installer. Parfait pour relire une PR rapidement.
Voir qui a écrit quoi — Blame Sur un fichier GitHub, cliquer sur "Blame" en haut à droite affiche ligne par ligne qui a écrit quoi et quand. Indispensable pour comprendre l'historique d'un fichier.
